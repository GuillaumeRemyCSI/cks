# LFS460 course exercises: trainer notes

`lfs460-single` (chapters 2-3) and `lfs460-cluster` (chapter 4 onwards) VMs (Google Cloud, europe-west6, Ubuntu 24.04.5, kernel 7.0 GCP, Kubernetes
v1.35.2, containerd 2.4, Cilium), as participant `trainer`. These notes list only what differs from
the course material, or what participants are likely to trip over. They do not reproduce the
exercises themselves.

Deployment: see [README.md](README.md#bare-vms-for-the-official-lfs460-exercises).

## Notes per exercise

### 2.1-2.4

- Reading exercises: every link resolves. The CIS benchmark download needs a registration
  (the exercise is optional).

### 2.5

- The `wget` of the course tarball works with the credentials printed in the course material; the
  file is identical to the one distributed to trainers.

### 3.1, 3.5 Supply chain and sandbox tools

- `neuvector.com` now redirects to SUSE Rancher Security. `theupdateframework/notary` redirects to
  `notaryproject/notary`, which is **archived** (its successor is Notation). UniK has had no commit
  since 2023 and PouchContainer is inactive: good material for the "how active is the community"

### 3.2 Trivy

- The course pins Trivy `v0.69.3` but fetches `install.sh` from the `main` branch. Install the same
  version from the release instead (see [7.1](#71-72-trivy)): download `trivy_0.69.3_Linux-64bit.deb`
  and `trivy_0.69.3_checksums.txt`, check with `sha256sum -c`, `sudo apt install ./trivy_0.69.3_Linux-64bit.deb`.
- The counts differ from the course material, as expected with a newer database: 64 for
  `knqyf263/vuln-image:1.2.3`, 407 for `nginx` (Debian 13), and `alpine` is **not** clean
  (1 MEDIUM on 2026-11-07). Tell participants the point is the method, not the numbers.

### 3.6 gVisor (`containerd-setup.txt`)

The script (`s_04/containerd-setup.txt`, its header still says Ubuntu 20.04) installs Kubernetes
**1.35.1** with **Calico**, unlike the chapter 4 scripts (1.35.2, Cilium). Two problems:

- **The gVisor downloads return 404**: `storage.googleapis.com/gvisor/releases/release/latest/x86_64/`
  no longer exists, and `wget -O` leaves empty `runsc` and `containerd-shim-runsc-v1` files without
  stopping the script. The pod then fails. Install gVisor from its signed apt repository instead:

  ```bash
  sudo rm -f /usr/local/bin/runsc /usr/local/bin/containerd-shim-runsc-v1
  curl -fsSL https://gvisor.dev/archive.key | sudo gpg --dearmor -o /usr/share/keyrings/gvisor-archive-keyring.gpg
  echo "deb [arch=$(dpkg --print-architecture) signed-by=/usr/share/keyrings/gvisor-archive-keyring.gpg] https://storage.googleapis.com/gvisor/releases release main" \
    | sudo tee /etc/apt/sources.list.d/gvisor.list
  sudo apt-get update && sudo apt-get install -y runsc
  ```

- **Cgroup driver mismatch**: the last `config.toml` written by the script drops
  `SystemdCgroup = true`, while the kubelet uses the `systemd` driver. Pods (kube-proxy,
  calico-kube-controllers) are then killed every 2-3 minutes and end in `CrashLoopBackOff`. Fix,
  then wait a minute for the pods to settle:

  ```bash
  printf '[plugins."io.containerd.grpc.v1.cri".containerd.runtimes.runc.options]\n SystemdCgroup = true\n' \
    | sudo tee -a /etc/containerd/config.toml
  sudo systemctl restart containerd
  ```

- `apt-get install containerd.io` asks for confirmation: answer `Y`.
- With these fixes, `simple-gvisor` runs and `uname -r` shows `4.19.0-gvisor` (the course shows
  `4.4.0`), against `7.0.0-1017-gcp` for a runc pod. `kubectl exec simple-gvisor -- dmesg` is a nice
  extra: it shows the gVisor boot messages.

### 3.7 Kubescape

- The course runs `install.sh` from the `master` branch, which installs the latest release (v4.0.20,
  published the day before). A pinned release is safer: download `kubescape_<version>_linux_amd64`
  and `checksums.sha256` from the GitHub release, check with `sha256sum -c`, then
  `install -m 755 kubescape_<version>_linux_amd64 ~/.kubescape/bin/kubescape` (validated with 4.0.16).
- `kubescape scan framework cis-v1.12.0` works (0 critical, 30 high, 105 medium, 3 low on a fresh
  cluster). Without the Kubescape operator (node-agent), the node checks (file permissions of etcd,
  PKI...) show `Action Required` and an error "failed to init host scanner": expected.
- `list frameworks` shows more frameworks than the course (AgentRuntimeHardening, ISM, newer EKS/AKS/GKE
  benchmarks).

### 5.7 Encrypting secrets

- `strings` is not installed on the VMs (no binutils): pipe `etcdctl get` into `grep -a` instead,
  or `sudo apt install binutils`.
- The tarball `encryptionconfig.yaml` holds the same AES key as the course material: make sure
  participants paste the key they generated at step 5.
- Step 10 shows `get .../first` where `second` is meant.
- Existing secrets stay in clear text until rewritten:
  `kubectl get secrets -A -o json | kubectl replace -f -`.

### 6.1 Network policies

- The `lfs460-cluster` firewall only allowed SSH: the NodePort tests from the participant's machine
  (steps 4 and 8, also 6.2-6.4 in a browser) need the NodePort range. Fixed in the
  `gcp_lfs460_nodes` / `lfs460_nodes` modules (tcp 30000-32767 from `CKS_ACCESS_CIDRS`); rerun
  `classroom.sh up lfs460-cluster` on environments deployed before the fix.
- `frontend` to `devapp` gives "connection refused": `devapp` is an `ubuntu` pod running `sleep`,
  nothing listens. Refused (not timed out) shows that egress is allowed.

### 6.2, 6.3 Ingress

- `hostname -i` returns `127.0.1.1` on these VMs (`/etc/hosts` entry): use `hostname -I` or
  `ip -4 addr show ens4` to get the node IP. The curl works with either since NodePorts listen on
  every address.
- The course installs ingress-nginx `controller-v1.8.1` (2023). It still works on 1.35, but the
  ingress-nginx project is retired: mention it.

### 6.4 Linkerd

- `install-edge` always installs the latest edge release (edge-26.11.1 on 2026-11-07, the course
  shows edge-26.2.1). All checks pass.
- `linkerd viz edges deploy` only lists deployments: a test client started with `kubectl run`
  appears with `linkerd viz edges pod`.

### 7.1, 7.2 Trivy

- The course installs Trivy with `curl ... trivy/main/contrib/install.sh | sh` (script from the
  `main` branch). A pinned release is safer: download `trivy_<version>_Linux-64bit.deb` and
  `trivy_<version>_checksums.txt` from the GitHub release, check with `sha256sum -c`, then
  `sudo apt install ./trivy_<version>_Linux-64bit.deb` (validated with 0.76.0).
- `--format spdx --output sbom-spdx.json` writes SPDX tag-value text, not JSON, despite the file
  name. `--format spdx-json` gives JSON. `trivy sbom` accepts both.

### 7.4 Tracee

- With chart `aqua/tracee` 0.24.1 the pods stay `0/1`: the readiness probe targets `:3366/healthz`,
  which is never opened. Apply the course note (remove the readiness probe from the DaemonSet):
  `kubectl -n tracee patch ds tracee --type=json -p '[{"op":"remove","path":"/spec/template/spec/containers/0/readinessProbe"}]'`.
- Detection then works: `TRC-102 Anti-Debugging detected` for `strace`, plus `TRC-1022 New
  executable dropped` from the `apt install`.
- Tracee and Falco are heavy for 2 vCPU nodes: uninstall Tracee before 7.5.

### 7.5 Falco

- **`helm install ... --set driver.kind=ebpf` fails** with chart 9.2.x (Falco 0.45):
  "driver.kind=ebpf is no longer supported". Use `--set driver.kind=modern_ebpf` (or omit it, it is
  the default).
- The rule needs a real terminal: `kubectl exec -it` from an interactive SSH session. The alert
  format changed (fields separated by `|`), the message is the same.

### 7.6 AppArmor

- `/var/log/syslog` exists on these VMs (rsyslog is active), so `aa-genprof` finds the events.
- At **Finish**, `aa-genprof` switches the kubectl profile to **enforce** mode. kubectl keeps working,
  with denials on a session-specific cgroup path (`/run/cilium/cgroupv2/.../session-N.scope/cpu.max`):
  a good example of a rule to glob. Remove or disable the profile afterwards so it does not get in the
  way of chapter 8.
- The image `fluentd/fluent` does not exist (ImagePullBackOff). It does not matter for the
  profiling, but `fluent/fluentd` avoids the confusion.
- **Steps 10-14 profile `/usr/bin/docker`, which is not installed** (the course scripts install
  containerd only). Either profile another binary (for example `/usr/bin/crictl`) or skip to
  step 15. Steps 15-17 (disable, re-enable) work with the kubectl profile.

### 8.1 Privilege escalation

- `kubectl run ... --serviceaccount webapp-sa` fails: the flag was removed from kubectl. Use
  `--overrides='{"spec":{"serviceAccountName":"webapp-sa"}}'` or a manifest.
- **`kubectl ... --token="$TOKEN"` with the admin kubeconfig still authenticates as
  `kubernetes-admin`**: the kubeconfig client certificate wins over the token
  (`kubectl auth whoami --token="$TOKEN"` shows it). As written, steps 3-4 succeed for the wrong
  reason and step 5 never shows the expected `Forbidden`. Use the token alone:

  ```bash
  kubectl --kubeconfig=/dev/null --server=https://<cp-ip>:6443 \
    --certificate-authority=/etc/kubernetes/pki/ca.crt --token="$TOKEN" get secrets -n kube-system
  ```

  With this, the broad ClusterRole lists the secrets, and after the fix the same command returns
  `Forbidden` while `get configmaps -n prod-a` works.

### 8.2 Incident response

- `https://testmyids.com/` fails (TLS error), so the logs never show `uid=0(root)...`. Use
  `http://testmyids.com/`.
- `kubectl logs --previous` fails when the container has never restarted: use `kubectl logs`.
- `crictl` and `ctr` must run **on the node hosting the pod** (usually `worker`), not on `cp`.
  On `worker`, `crictl` warns that `/etc/crictl.yaml` is missing; it still works.
- The drain evicts the ingress-nginx controller and the Linkerd proxy injector if they run on
  `worker`: they come back on `cp`, and return after the uncordon.
